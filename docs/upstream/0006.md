# text: render inline code spans in the theme's mono font

An inline code span (`` `like this` ``) is styled through
`TextViewStyle::inline_code_highlight()`, which returns a gpui `HighlightStyle`.
A `HighlightStyle` carries color, weight, style, background, underline,
strikethrough and fade — but no font family. So inline code gets the code
background and nothing else: it is shaped in the body font, while fenced code
blocks (which go through a `div().font_family(theme.tokens.typography.mono)`)
render in the mono font. The two kinds of code in one document disagree on the
typeface.

## Reproduction

Set a distinct sans and mono family on the theme (any pair that differ visibly,
e.g. `Noto Sans` / `JetBrainsMono Nerd Font`) and render:

```markdown
Body text with `inline_code()` in it.

```rust
fn fenced() {}
```
```

The fenced block is mono; the inline span is the body sans, with a mono-less
accent background. Every inline code span in a 3 900-note vault rendered this
way.

## Fix

Reworked after review (fork branch `feat/inline-code-mono-font-family` @ `314efe8`
on `928c3eb7`; [rework notes](https://github.com/longbridge/gpui-kit/pull/2949#issuecomment-5551113807)).
The parallel `code_ranges` vector from the first revision is gone: the highlights
payload is now `InlineHighlight { style: HighlightStyle, font_family: Option<SharedString> }`,
threaded everywhere `(Range<usize>, HighlightStyle)` was (`Inline`, `InlineFlowItem`,
`MeasureItem`, `LineFragmentKind`, `PositionedFragment`, both `Paragraph` builders).
`inline::combine_highlights` cuts every span at its endpoints so nothing straddles a
code boundary, and `text_runs` is the single run loop plus `run.font.family = family`
when the highlight names one; `runs_for_highlights` is folded into it and the two
mark-to-highlight loops in `node.rs` share `mark_highlight`.

The family is a style field, not a theme read from base: `TextViewStyle::inline_code_font_family:
Option<SharedString>` (`from_theme` sets `theme.tokens.typography.mono`, `Default`
the token default, `None` keeps the body face); the component `TextViewStyle` gains
the same optional field resolved in `resolve_component_style`, with the theme adapter
filling it from `theme.mono_font_family`. Both measurement paths shape code spans in
that family: `inline_flow::line_ranges` emits each family-bearing span as a
`LineFragment::element` at its shaped width so the wrapper breaks around it, and the
table max-content pass (`measure_table_columns`) runs `text_runs` over the cell's
inline highlights. Tests against a `WideMonoTextSystem` (mono at twice the body
advance) cover both: `inline_code_near_the_wrap_width_does_not_overflow_the_flow`
and `table_column_of_inline_code_cells_fits_the_mono_width`.
`crates/base/src/text/{inline,inline_flow,node,style}.rs`,
`crates/component/src/text/{compat,mod,style}.rs`, +723 −188, no gpui core change.
