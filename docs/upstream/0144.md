# Retire an abandoned completed parse result on background

Related residuals: [editing lag](https://git.oklabs.uk/BeFeast/okilum/issues/2803)
and [large edit tools](https://git.oklabs.uk/BeFeast/okilum/issues/2804).
Source baseline: `41be1f35d1b36bcc922188f1cd3a508ad4c2104a`.
Adapter owner: `longbridge/gpui-kit`, pinned upstream
`928c3eb776a3d733d9b771f7dea27a6a79242ced`, cumulative patches through 0143.
The app lock resolves tree-sitter **0.26.13**, gpui-pre-scheduler **0.3.3** and
async-task **4.7.1**. This patch changes neither GPUI core nor tree-sitter.

## Reachable ownership boundary

`TreeSitterInputHighlighter::update` stores a foreground `Task<()>` whose
continuation awaits the existing background parse `Task`. `Context::spawn_in`
explicitly polls its continuation on the main thread. The parser future owns
immutable reuse inputs; its completed output owns the new Tree, injection layers
and fold ranges. These are distinct lifetimes.

The scheduler's spawned `Task` delegates to async-task. Dropping an incomplete
foreground handle sets CLOSED and schedules its future's eventual destruction
on foreground. When that future contains an already-completed background Task,
async-task's `set_detached` claims the stored output and drops it **on the dropping
executor**. Running the producer on background does not establish the output's
destruction executor. The relevant pinned code is:

- `gpui-pre-0.3.3/src/app/context.rs::Context::spawn_in`;
- `gpui-pre-scheduler-0.3.3/src/executor.rs::{BackgroundExecutor::spawn_with_priority, Task::poll}`;
- `async-task-4.7.1/src/task.rs::{Task::drop, set_canceled, set_detached}`;
- `async-task-4.7.1/src/raw.rs::RawTask::run`, CLOSED and Ready branches.

The deterministic app control completes the **real existing** parser task using
`TestScheduler::tick_background_only`, before the foreground awaiter receives its
next poll. A real superseding source edit replaces the stored foreground Task.
There is no worker-side gate/await, output proxy or additional Tree clone.
Borrowed root TSNodes identify the existing output's TSTree handles; counters in
a private copy of the actual app dependency count their deletes and freed nodes.

On the baseline, a UTF-8/CRLF HTML source produces **27 output Tree handles,
26 injection layers and 26 fold ranges**. This control explicitly enables the
existing folding option; the app plain-file folding default remains false.
Immediate Task handle drop deletes
none. Deferred foreground-future destruction deletes **all 27 candidate Trees**
and frees **7,599 subtrees**. The background future has already returned and been
destroyed; its Task's stored output is the remaining owner. Cancelled await,
publication and fold callbacks are all unfired. Exact pending byte/point ranges,
semantic samples and byte-exact one Undo remain valid after the cleanup drain.

These are work/ownership counts, not durations, native key-to-paint, RSS or an
estimate of natural occurrence. They do not attribute or remove the retained
64–67 ms aggregate highlighter phase. The separate broad `Tree::edit` traversal
and necessary parser/retirement sharing are unchanged.

## Bounded fix

The background output is now a private `BackgroundParseResult` owning precisely
its existing `(Tree, injection layers, fold ranges)` tuple and a background
executor handle. On acceptance, `into_inner` moves the tuple out once, leaving
an empty owner; publication, source admission and existing replaced/rejected
retirement follow their original order. There is no extra Tree or source clone.

If the completed result is abandoned instead, its Drop moves the tuple into one
detached task on the existing background executor. This covers output-storage
cleanup when the foreground awaiter is cancelled, including races with producer
completion. Detaching retirement prevents subsequent parse cancellation from
cancelling cleanup. The tuple keeps its original field destruction order.
Neither branch captures a UI entity, Rc, parser or source/history mutation.

Early parser failures and progress cancellation still return None. Any parser
locals then retire under their existing background scopes. Parse debounce,
reuse inputs, synchronous small-file policy, pending Tree::edit coordinates,
query source guard/exact fallback and fold/style publication remain unchanged.
A consumed output does not schedule an abandoned-result cleanup task.

The payload is finite and already existed. Cleanup may extend its lifetime until
the existing executor schedules it, as with patch 0141. This adds no global queue,
new worker, permit or aggregate RSS bound. The executor handle supplies the
existing cleanup destination; it is not a new scheduling service. Shutdown when
an executor cannot run, final highlighter teardown, source Rope retirement and
other owners' final releases are separate mechanisms, not solved here.

## Regression controls

Two checked-in adapter controls exercise the real async parse branch with
Markdown, at least 24 actual Rust injections, Hebrew, emoji, combining marks and
CRLF. They stop the single-task scheduler immediately when the actual worker
constructs its output and returns, then either cancel the unpolled foreground
awaiter or allow publication. Unrelated queued background work is not treated
as a parse-readiness signal. A test-only creation counter
proves actual output readiness; the existing real InjectionLayer destructor
meter proves zero syntax-layer destruction during cancellation and complete
background cleanup after drain. A deliberate local destruction fires that same
meter as a positive control. Pending source, root byte/point coordinates,
semantic captures and fold queries match an independently edited reference;
accepted semantics additionally match a fresh parse over the entire source.

The app-lock C-counter control independently covers actual Reader/source edits,
all marked candidate handles, actual subtree frees, cancelled publication/fold
callbacks and one Undo. Its regression asserts zero foreground candidate deletes
and all actual candidate cleanup in the abandoned background scope. The compiled
old-production negative restores the exact baseline adapter plus identical
observers, leaving the regression assertion unchanged; it must fail on actual
foreground deletion, not compilation or an unfired readiness condition.

This is headless deterministic lifecycle validation, not native acceptance.
No repeated ownership matrix, functional large-tools flow, native fallback,
installer or device checks are required by this lifetime-only change.

## Upstream plan and remaining scope

The fix belongs in `longbridge/gpui-kit`'s adapter. A completed parse output that
retains its own disposal destination is general to this foreground/background
ownership pattern. Keep it as a cumulative vendor patch and propose the minimal
owner plus lifecycle controls upstream only after separate authorization. No
upstream issue/PR is opened by this change.

Broad pending-coordinate representation/tree-sitter algorithm changes need a
separate concrete design decision. XML, natural owner residence, other long-line
materialization/comparison/glyph/platform work, native latency and original
reporter acceptance remain unfinished under the same owner. Previous functional
Validate/Format/Repair/Cancel/stale/one Undo/post-Repair/menu/durability and delivery
receipts remain evidence of their own tested scope; they are not rerun or expanded
into a new acceptance claim here. Both reporter issues remain open.
