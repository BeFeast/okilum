# Prefer color emoji fonts for Unicode emoji presentation

## Problem

A code font can contain monochrome glyphs for U+2705 and U+274C. Coverage-based
fallback then keeps them monochrome, although both have Emoji_Presentation=Yes.
The same problem affects body text, editor Source and rendered editor text.

## Change

Apply one Unicode presentation policy to text runs before shaping, and use the
same shaped emoji clusters when measuring wrap fragments. Default emoji, VS16,
ZWJ/skin-tone/flag and keycap sequences use the platform color emoji face. VS15
retains text presentation; text-default U+2714 stays in the authored face unless
VS16 is present. A grapheme is kept in one font run even if an input syntax run
boundary falls inside it. Text and UTF-8 offsets are unchanged.

The patch uses existing GPUI TextRun, WindowTextSystem and LineFragment APIs.
It changes gpui-kit base only; GPUI core is unchanged. ASCII avoids the Unicode
scan and ordinary lines do not create an additional shaping cache. The Unicode
properties crate is already in the locked dependency graph (0.1.4).

## Synthetic reproduction and tests

A C# code-block-style run containing `// ✅ ❌ ✔ ✅︎` must select the system emoji
font for the first two symbols, even if the mono face covers every code point.
The plain check mark and explicit text selector stay mono. A mock platform with
different advances for mono/body faces proves the font choice affects shaping.
Wrapping a ZWJ/skin-tone sequence must measure the same width as the painted runs
and never split the cluster. Additional property/UTF-8/decoration tests cover
VS16, flags, keycaps and non-emoji text containing ZWJ.
